<objective>
Add the global, cross-band Tracks tab (TRACK-06): repurpose the placeholder "Songs" bottom-nav tab into "Tracks", showing a flat list of every track across every band the user belongs to, with a band-name badge per row and a filter dropdown to narrow to one band.

**Architecture note (singular -> plural transition):** this plan introduces the phase's only per-entity -> cross-entity transition — a single band's track list (Plan 01/02, keyed by `bandId`) versus a view spanning *all* of a user's bands. Decision: **add-alongside**, not promote. The primary identity/key model for a track stays per-band-scoped (`(bandId, trackId)`, matching every mutation endpoint — create/update/delete all live under `/api/band/{bandId}/track/...`). The global view is an additive, read-only aggregate sourced from a separate endpoint (`GET /api/track/list`, `UserTrackListItem` — a distinct, wider shape carrying `bandId`/`bandName`) and a separate provider (`UserTracksListData`), not a promotion of the per-band model to "primary". Rationale: every write operation is still band-scoped by the API contract; promoting the global view to primary would require inventing a cross-band identity the backend doesn't expose.

**Known assumption carried from research:** 03-RESEARCH.md flagged `GET /api/track/list`'s live backend readiness as unconfirmed (Assumption A1). This plan's own read of `lib/api/publicapi.yml` (lines 312-328, 819-851) confirms the endpoint, its `BandIdFilter` query parameter, and `ListUserTracksResponseBody`/`UserTrackListItem` schemas are already defined in the API contract — so the client is built against a real, committed contract, not an invented shape. Whether the backend has *implemented* it is out of this plan's control; if it hasn't, the existing cache-first + `ApiException`/`AsyncError` handling degrades gracefully to the standard "Couldn't load tracks" + Retry state rather than crashing.

Purpose: close the last Phase 3 requirement so the full Tracks feature set (TRACK-01 through TRACK-06) is complete.
Output: `TracksScreen` (replacing `SongsScreen`), the `listUserTracks` API method, `ApiClient` query-parameter support, and the `UserTracksListData`/`SelectedBandIdFilter` providers.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client -> Cadence backend API | `GET /api/track/list` (optionally with a `bandId` query filter) crosses the network; response items span every band the user belongs to |
| App -> device-local Hive tracksBox | The global list is cached alongside per-band track data in the same box, keyed separately (`user_tracks_*`) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-09 | Information Disclosure | GET /api/track/list response scope | low | accept | Server is responsible for scoping the returned `items` to only the requesting user's own bands; the client trusts and renders exactly what the server returns, adding no client-side band-membership filtering of its own (would be redundant and could itself introduce a bug masking a server-side scoping error). |
| T-03-10 | Tampering | `bandId` query parameter (client-supplied filter) | low | accept | The filter only narrows what's *displayed* from an already user-scoped response set (the server still enforces which bands the caller may see); passing an arbitrary `bandId` a user doesn't belong to can at most yield an empty filtered result, not leak another user's data, since the server's own membership scoping governs the full `items` set regardless of the filter value. |
| T-03-11 | Denial of Service | New `ApiClient.queryParameters` construction (`Uri.replace`) | low | accept | `Uri.replace(queryParameters: null)` is a no-op on the existing query component (Dart SDK behavior); this change is purely additive and exercised by every existing call site's tests continuing to pass unmodified. |
</threat_model>
