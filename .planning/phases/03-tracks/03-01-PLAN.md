<objective>
Stand up the per-band track catalog end-to-end: a band member can view a band's tracks, add a new one, and open a track's full detail page. This is the tracer slice for Phase 3 — it wires every layer (API contract call, Hive cache, Riverpod family providers, three new screens, and the Band Detail navigation entry point) for TRACK-01/02/03 in one production-quality path, mirroring Phase 2's BandsListData/BandDetailData pattern exactly rather than inventing a new shape.

Track edit/delete (TRACK-04/05) and the global cross-band Tracks tab (TRACK-06) build on top of this plan's artifacts in Plans 02 and 03.

Purpose: prove the Riverpod + Hive cache-store pattern generalizes to a *third* per-band-keyed entity (after bands and, within this phase, tracks) without architectural surprises, before expanding into edit/delete/global-view.
Output: `TrackListScreen`, `CreateTrackScreen`, `TrackDetailScreen`, the `TrackListData`/`TrackDetailData` providers, and their `CacheService`/`PublicApi` backing methods — all reachable from `BandDetailScreen`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client -> Cadence backend API | `PublicApi.listBandTracks`/`getBandTrack`/`createBandTrack` cross the network; responses are untrusted until parsed/typed by the client |
| User input -> CreateTrackScreen form | Title/artist/duration/tempo/key/notes are untrusted free text entered on-device before being sent to the server |
| App -> device-local Hive tracksBox | Cached track lists/details persist in the app's private sandboxed storage |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | POST /api/band/{bandId}/track (createBandTrack) | low | accept | Server is the authoritative validator of all submitted fields (title/artist/duration/tempo/key/notes); client-side `TextFormField` validators are UX only, not a security boundary; `ApiException` surfaces any 400 rejection to the user. |
| T-03-02 | Information Disclosure | tracksBox Hive cache (device-local track list/detail) | low | accept | Box lives in the app's OS-sandboxed private directory, same accepted-risk pattern already established for profileBox/homepageBox/bandsBox in Phase 1/2; no new sensitive fields introduced (tracks carry no auth/PII data). |
| T-03-03 | Elevation of Privilege | Track view/create access (any band member, no owner-only path) | low | accept | REQUIREMENTS.md TRACK-01/02/03 carry no owner qualifier (unlike BAND-05); server enforces band-membership scoping on all `/api/band/{bandId}/track/...` routes; client adds no ownership gate on the new "Tracks" nav entry, matching the requirement. |
| T-03-04 | Denial of Service | Malformed JSON response from track list/detail endpoints | low | accept | `ApiClient.send()`'s existing `jsonDecode` + status-code handling (unchanged by this plan) already wraps decode failures as thrown exceptions caught by the UI's error state — same pattern as Phase 1/2, no new attack surface. |
| T-03-05 | Tampering | Man-in-the-middle on track API calls | medium | accept | HTTPS is enforced via the existing `ApiClient`/`AppConfig.apiBaseUrl` (Phase 1 infra, unchanged here); certificate pinning is out of ASVS L1 scope and explicitly deferred (03-RESEARCH.md Security Domain). |
</threat_model>
