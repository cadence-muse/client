# Phase 06.1 Plan 01: API Contract Catch-Up (RemoveSetlistTrack Batch + ListUserTracks/ListUserSetlists POST) Summary

**Migrated removeSetlistTrack to the batch DELETE .../tracks endpoint and listUserTracks/listUserSetlists from GET to POST, matching the fe72e78 publicapi.yml schema update with zero regressions across the 315-test suite.**

## Performance
- **Duration:** ~15min

## Accomplishments
- `PublicApi.removeSetlistTrack` now calls `DELETE /api/band/{bandId}/setlist/{setlistId}/tracks` with body `{'trackIds': [trackId]}`, replacing the removed single-track `DELETE .../track/{trackId}` route. Public signature unchanged.
- `PublicApi.listUserTracks` and `PublicApi.listUserSetlists` now call `POST` instead of `GET` on `/api/track/list` and `/api/setlist/list` respectively, with `bandId` still sent as a query parameter and a new optional `searchQuery` parameter sent in the JSON body (per `?`-prefixed conditional-spread convention) when non-null.
- Created `test/api/public_api_test.dart` — 8 new focused unit tests proving the exact method/path/query/body wire contract for all three migrated methods.
- Corrected `setlist_detail_screen_test.dart`'s existing removeSetlistTrack widget test to assert the new batch DELETE path + body, keeping the tap-to-remove UI flow regression-tested end-to-end.
- Added `POST`-method regression assertions to the existing `tracks_provider_test.dart`/`setlists_provider_test.dart` bandIdFilter tests — new coverage that would have caught this exact GET/POST mismatch had it existed before.
- Confirmed via full-suite run that `AddSetlistTracks`'s 204->200 response-code spec change requires no client code change (`ApiClient.send` only branches on `statusCode >= 400`), and that `ListBandTracks`/`ListBandSetlists`/`ChangeUserPassword`/`RotateBandInviteCode`/`TransferBandOwnership` remain untouched.

- `searchQuery` added to `listUserTracks`/`listUserSetlists` for wire-schema completeness only; no UI collects or sends it in this phase (explicitly out of scope per the plan's objective).
