# Phase 06.1: Code Review Report

**Reviewed:** 2026-08-21T07:25:39Z
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

This phase migrated `removeSetlistTrack` from a single-track `DELETE .../track/{trackId}` call to the batch `DELETE .../tracks` endpoint (body `{trackIds: [trackId]}`), and migrated `listUserTracks`/`listUserSetlists` from `GET` to `POST` with an optional `searchQuery` body field, keeping `bandId` as a query parameter — all per the `fe72e78` `publicapi.yml` update.

I cross-checked every touched method against `lib/api/publicapi.yml`'s current schema (`RemoveSetlistTracksRequestBody`, `ListUserTracksRequestBody`/`ListUserTracksResponseBody`, `ListUserSetlistsRequestBody`/`ListUserSetlistsResponseBody`, and the `BandIdFilter` query parameter definition) and found the HTTP method, path, query-parameter placement, and body shape all correct. I also verified the Dart null-aware map-entry syntax (`{'searchQuery': ?searchQuery}`) actually omits the key when `searchQuery` is `null` (confirmed via a standalone `dart run` repro — produces `{}`, not `{'searchQuery': null}`), so the optional-field omission semantics are correct. `flutter analyze` on the touched files is clean, and all listed tests pass (`flutter test` — 57/57 passing across the five files). I found no other call sites in `lib/` still assuming the old single-track DELETE path or GET method.

No correctness or security defects found. The findings below are test-coverage gaps in the new wire-contract tests and a code-duplication/reuse note in `public_api.dart`.

## Warnings

### WR-01: No test asserts the JSON request body when neither `bandIdFilter` nor `searchQuery` is given

**File:** `test/api/public_api_test.dart:100-120` (mirrored at `167-187` for `listUserSetlists`)
**Issue:** The "no bandIdFilter and no searchQuery" tests for both `listUserTracks` and `listUserSetlists` only assert `capturedMethod` and the absence of the `bandId` query parameter — they never inspect `request.body`. The correctness of `body: {'searchQuery': ?searchQuery}` omitting the key when `searchQuery` is `null` (rather than serializing an explicit `null`, or a stray `Content-Type` mismatch) is exactly the kind of subtlety this migration introduces, and it's currently unverified by any test. If a future refactor of this null-aware spread accidentally changes to unconditionally include the key (e.g. `'searchQuery': searchQuery`, matching the pattern used elsewhere in the file for non-optional-omission fields like `updateBandTrack`), no test in this suite would catch it.
**Fix:**
```dart
test(
  'calling with no bandIdFilter and no searchQuery sends an empty JSON body',
  () async {
    Map<String, dynamic>? capturedBody;
    final api = PublicApi(
      buildApiClient((request) async {
        capturedBody = jsonDecode(request.body) as Map<String, dynamic>;
        return http.Response(jsonEncode({'items': <dynamic>[]}), 200);
      }),
    );

    await api.listUserTracks();

    expect(capturedBody, <String, dynamic>{});
  },
);
```
(same for `listUserSetlists`)

### WR-02: No test exercises `bandIdFilter` and `searchQuery` together

**File:** `test/api/public_api_test.dart:74-139` (`listUserTracks` group), `141-206` (`listUserSetlists` group)
**Issue:** Every test in both groups exercises `bandIdFilter` and `searchQuery` in isolation. There's no test confirming that calling `listUserTracks(bandIdFilter: 'b1', searchQuery: 'wonderwall')` produces both the `bandId` query parameter *and* the `{searchQuery: 'wonderwall'}` body simultaneously — the case that most directly exercises "the GET→POST migration kept `bandId` as a query param while adding an optional body field," which is the actual behavior change under test in this phase.
**Fix:**
```dart
test(
  'calling with both bandIdFilter and searchQuery sends both as query '
  'parameter and JSON body respectively',
  () async {
    String? capturedBandId;
    Map<String, dynamic>? capturedBody;
    final api = PublicApi(
      buildApiClient((request) async {
        capturedBandId = request.url.queryParameters['bandId'];
        capturedBody = jsonDecode(request.body) as Map<String, dynamic>;
        return http.Response(jsonEncode({'items': <dynamic>[]}), 200);
      }),
    );

    await api.listUserTracks(bandIdFilter: 'b1', searchQuery: 'wonderwall');

    expect(capturedBandId, 'b1');
    expect(capturedBody, {'searchQuery': 'wonderwall'});
  },
);
```

## Info

### IN-01: `removeSetlistTrack`'s second test is a low-value duplicate of the first

**File:** `test/api/public_api_test.dart:58-71`
**Issue:** `'a 204 response resolves without throwing'` re-exercises the exact same request/response as the preceding test (`'sends DELETE ... with body {trackIds: [trackId]}'`, lines 27-56), which already implicitly proves the call completes without throwing (an unhandled exception would fail that test too). This second test adds no coverage beyond what's already asserted, just extra maintenance surface.
**Fix:** Either drop this test, or repurpose it to assert something the first test doesn't — e.g. a non-empty multi-item batch response, or a 400-path negative test (`expectLater(..., throwsA(isA<ApiException>()))`) which is currently absent for this method entirely.

### IN-02: `listUserTracks` and `listUserSetlists` are near-duplicate implementations

**File:** `lib/api/public_api.dart:239-250` and `395-406`
**Issue:** The two methods are structurally identical (same signature shape, same query-parameter construction, same `body: {'searchQuery': ?searchQuery}` line, same response unwrapping) apart from the path string and item type. The doc comment on `listUserSetlists` even says "Mirrors `listUserTracks` exactly," acknowledging the duplication. This phase's migration touched both methods in lockstep and reinforced the duplication rather than reducing it — a good opportunity to extract a shared private helper (e.g. `_listWithBandFilter(path, bandIdFilter, searchQuery)`) was available but not taken.
**Fix:**
```dart
Future<List<Map<String, dynamic>>> _postListWithFilter(
  String path, {
  String? bandIdFilter,
  String? searchQuery,
}) async {
  final response = await _client.send(
    'POST',
    path,
    queryParameters: bandIdFilter == null ? null : {'bandId': bandIdFilter},
    body: {'searchQuery': ?searchQuery},
  );
  return (response!['items'] as List).cast<Map<String, dynamic>>();
}

Future<List<Map<String, dynamic>>> listUserTracks({
  String? bandIdFilter,
  String? searchQuery,
}) => _postListWithFilter(
  '/api/track/list',
  bandIdFilter: bandIdFilter,
  searchQuery: searchQuery,
);

Future<List<Map<String, dynamic>>> listUserSetlists({
  String? bandIdFilter,
  String? searchQuery,
}) => _postListWithFilter(
  '/api/setlist/list',
  bandIdFilter: bandIdFilter,
  searchQuery: searchQuery,
);
```
Not a functional defect — the current duplicated form is correct — but worth consolidating given the pattern will likely be touched again (e.g. if `searchQuery` gains UI wiring later, per the existing doc comment noting it's "not yet driven by any UI in this phase").
