<objective>
Wire the three destructive band-membership mutations end-to-end: `DELETE /api/band/{bandId}` (BAND-05, owner-only, type-to-confirm), and `DELETE /api/band/{bandId}/remove-member/{userId}` for both self-leave (BAND-08) and owner-remove (BAND-09), each with correct owner-gating (D-01/D-02/D-03) and the confirmation pattern D-13/D-14 prescribe.

Purpose: These three share the same `removeMember`/`deleteBand` API surface, the same owner-vs-member gating logic, and the same `BandDetailScreen` real estate — building them together avoids three separate passes over the same owner-gating helper and the same file.
Output: Owner-gated Delete/Leave/Remove actions on `BandDetailScreen`, each with the correct confirmation friction and post-success navigation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flutter app <-> API server | `DELETE /api/band/{bandId}` and `DELETE /api/band/{bandId}/remove-member/{userId}` cross the network boundary; these are the only two irreversible/destructive mutations in Phase 2 |
| Client-side UI gating <-> server-side authorization | The client hides Delete/Remove-member for non-owners, but the server remains the authoritative enforcer (403 on a mismatched attempt) |

| T-02-01b | Tampering / Elevation of Privilege | `lib/features/bands/band_detail_screen.dart` (`_isOwner` gate, re-confirmed from 02-02-PLAN.md's T-02-01) | high | mitigate | `_isOwner` compares server-returned `ownerId` (from `BandDetailData`) to server-returned `id` (from `profileDataProvider`) — never a client-editable value; the server independently enforces ownership on `deleteBand`/`removeMember` (403 `permission_denied` if the client's hidden-button gate were ever bypassed), so a client-side UI bug can hide/show a button incorrectly but cannot actually elevate privilege |
