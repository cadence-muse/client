<objective>
Wire `GET /api/band/list` end-to-end — API method, Hive cache box, Riverpod provider, and a real `BandsScreen` — replacing the current hardcoded `_mockBands`/`Band` stub with the actual API-backed, cache-first band list (BAND-01).

</objective>

<assumption_delta_decision>
Primary noun: "band" — the phase introduces a one-to-many "user belongs to multiple bands" relationship for the first time.
Decision: no-change
Rationale: Phase 1 established a single-user-session model (one `AuthSession`/`ProfileData` per device, keyed off the persisted token). BAND-01's band list is a one-to-many relationship *from* that single existing user, not a second user identity, a competing session model, or a promotion of "band" to a session-scoping concept — it's the same shape `HomepageData.bandsCount` already anticipated. `BandsListData` (this plan) and `BandDetailData` (02-02) key off the single existing `AuthSession`'s token exactly like `ProfileData`/`HomepageData` already do; no parallel identity/session model is introduced.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flutter app <-> API server | `GET /api/band/list` crosses the network trust boundary; response is untrusted input decoded and cached client-side |
| App <-> on-device Hive storage | `bandsBox` persists decoded API responses to disk; a compromised/rooted device could read this file |
