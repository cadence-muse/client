## Typography

Material Design 3 text theme hierarchy. All roles inherit from Material's `TextTheme`.

**Actively used this phase (4 sizes):**

| Role | Flutter Token | Size | Weight | Line Height |
|------|---------------|------|--------|-------------|
| Heading | headlineMedium | 28px | 500 (medium) | 1.2 |
| Body | bodyLarge | 16px | 400 (regular) | 1.5 |
| Body | bodyMedium | 14px | 400 (regular) | 1.5 |
| Label | labelLarge | 14px | 500 (medium) | 1.2 |

**Usage specifics for this phase:**

- **headlineMedium** (28px, 500): Band name, screen titles (e.g., band detail, create band form heading)
- **bodyLarge** (16px, 400): Primary list items (band names in list), section labels
- **bodyMedium** (14px, 400): Secondary text (member count, invite code display, supporting details)
- **labelLarge** (14px, 500): Button labels (CTA, actions), dialog titles

**Inherited from Phase 1 (out of scope for Phase 2 implementation):**
- displayLarge (57px) — not used in Phase 2
- headlineSmall (24px) — not used in Phase 2

**Line heights:** Fixed at Material defaults (1.2 for headings/labels, 1.5 for body). No adjustments per phase.

**Source:** Phase 1 profile_screen.dart uses `Theme.of(context).textTheme.headlineMedium`, establishing the pattern. home_screen.dart confirms `bodyLarge`.

## Color

**Primary Palette (Material 3 green seed):**

| Role | Usage | Notes |
|------|-------|-------|
| Primary | CTA buttons (Create Band, Join Band, Confirm actions), active icons, selected states | Green, generated from ColorScheme.fromSeed(seedColor: Colors.green) |
| Secondary | Secondary buttons, card backgrounds, inactive/secondary UI elements | Material-generated secondary from theme |
| Tertiary | Accent elements, focus states, secondary highlights | Material-generated tertiary from theme |
| Surface | Screen background, list backgrounds | Material light/dark surface color |
| Error | Destructive actions only (Delete Band, Leave Band, Remove Member), error messages | Material red (error) |

**60/30/10 Split:**

- **60% Dominant Surface:** Page backgrounds, card surfaces, list backgrounds (white in light, surface in dark)
- **30% Secondary:** Card containers, section dividers, inactive states (Material's secondary/tertiary generated colors)
- **10% Accent:** Primary CTA buttons (Create, Join, Confirm), success states — reserved explicitly for user-initiated creation and safe confirmations only

**Accent Reserved For:**
- Primary CTA: "Create Band" FAB and button
- Primary CTA: "Join Band" dialog submit
- Safe confirmation: "Join" button in join dialog
- Active/focused states in forms
- Material-generated interactive focus rings

**NOT used for:**
- Secondary/tertiary buttons (use Material's outline or text styles)
- Navigation state (handled by Material's BottomNavigationBar)
- Success messaging (inline text only, no color highlighting for this phase)

**Destructive Color (Error Red):**
- "Delete Band" button background or outline (red/error color from theme)
- "Leave Band" text/outline (red)
- "Remove Member" text/outline (red)
- Error message text in dialogs or error states
- Confirmation text: e.g., "Type [band name] to confirm deletion"

**Source:** Phase 1 app_theme.dart establishes green seed; existing profile_screen.dart uses ElevatedButton (primary), icon colors (primary), and Material's standard patterns.

## UI Considerations

State coverage and edge cases for this phase:

| Category | Element(s) | Status | Resolution |
|----------|------------|--------|-----------|
| **Empty** | Band list (no bands) | ✅ covered | Empty-state heading + body + "Create Band" CTA render when `GET /api/band/list` returns empty `items[]` |
| **Loading** | Band list, band detail | ✅ covered | Material CircularProgressIndicator shown in center of body while fetching (cache-first pattern: cached data shown immediately if present; loading overlay only on first fetch) |
| **Error** | Band list, band detail, create/join/delete mutations | ✅ covered | Centered error layout with heading, body, and "Retry" button. Matches Phase 1 profile/home error pattern (ApiException caught at UI layer, generic "Couldn't load" + connection advice) |
| **Populated** | Band list items | ✅ covered | Material ListTile with CircleAvatar (band initial), band name (bodyLarge), no subtitle (members/genre removed per D-05, real API schema is id+name only) |
| **Overflow** | Long band names in list/detail | 🧪 backstop | Band names truncate with ellipsis (maxLines: 1, overflow: TextOverflow.ellipsis) — visual test required to verify readability at typical name lengths (10–40 chars expected) |
| **Overflow** | Invite code display | 🧪 backstop | Invite code (typically UUID ~36 chars) fits in single line or wraps gracefully. Recommend monospace font for code. Visual test for various screen widths (mobile portrait/landscape) |
| **Long-text** | Member names in detail | 🧪 backstop | Member usernames (typically 4–20 chars) truncate if exceed space. Visual test for edge case (very long username in narrow list column) |
| **Zero-one-many** | Band members list | ✅ covered | Detail screen shows "Members" section with count and list. Empty members list unlikely (creator always member), but handled gracefully (empty section or "No members" message) |
| **Zero-one-many** | Destructive actions visibility | ✅ covered | "Delete" and "Remove member" hidden for non-owners (D-02); "Leave" hidden for owners (D-03). Actions conditionally rendered based on `Band.ownerId === currentUserId` |

**Notes:**
- All error states and empty states reference copywriting contract above — no separate text needed here.
- Phase 1 established backstop tests for long-text truncation in profile_screen.dart (username ellipsis); extend pattern to band names and member usernames.
- Loading state is non-intrusive: if cached data exists, show cached + silent background refresh (no spinner overlay).

## Styling Patterns & Constraints

### Bands List Screen

- **Layout:** Scaffold with AppBar ("Bands" title) + ListView.separated for band list + FAB
- **List item:** Material ListTile with leading BandAvatar (initial), title (band name, bodyLarge), trailing chevron, onTap → band detail screen
- **Spacing:** 16px item padding (Material ListTile default), 8px divider height (consistent with Phase 1)
- **Empty state:** Centered column with heading (headlineMedium), body (bodyMedium), and "Create Band" button (all 24px padding, lg spacing) — mirrors Phase 1 home_screen.dart pattern
- **Loading state:** Material CircularProgressIndicator centered (cache-first: only shown on first fetch or cache miss)
- **Error state:** Centered column with heading (headlineMedium), body, "Retry" button — matches Phase 1

### Band Detail Screen

- **Layout:** Scaffold with AppBar (band name as title, no actions) + ListView for content
- **Focal point:** Band name section (heading + avatar) positioned at top of scrollable content — primary visual anchor for identifying which band is displayed
- **Sections:** 
  1. Band info (name heading, avatar)
  2. Members section (label + member list)
  3. Invite code section (label + code display + copy button)
  4. Actions (Edit, Leave, Delete [owner only])
- **Spacing:** 24px padding around sections, 16px between section subsections, 8px between list items
- **Member list items:** ListTile or simple Row with username (bodyMedium) and remove icon (owner only, red)
- **Copy button:** Simple "Copy" text button or icon button next to invite code
- **Actions:** Rows of buttons at bottom or grouped in a section. Destructive actions (Leave, Delete) use red/error color

### Create Band Screen

- **Layout:** Scaffold with AppBar ("Create a new band" title) + form in body + create button
- **Form fields:** Single text input for band name (labelLarge label, 16px padding)
- **Button:** "Create" ElevatedButton (primary color), full width or standard width
- **Spacing:** 24px top padding, 16px between form fields and button
- **Cancel:** Back button in AppBar (standard Material behavior)

### Join Band Dialog

- **Layout:** Material AlertDialog with title, content, actions
- **Title:** "Join a band"
- **Content:** Text input field with label "Invite code" (hint: "Paste the code here")
- **Actions:** "Cancel" TextButton, "Join" ElevatedButton (primary)
- **Spacing:** Material defaults (16px padding, 8px between buttons)

### Confirm Dialogs

All follow Material AlertDialog pattern:

**Delete Band (type-to-confirm):**
- Title: "Delete [band name]?"
- Body: Explanation + "Type the band name to confirm. This action cannot be undone..."
- Form field: "Band name" input (initially empty)
- Actions: "Cancel" TextButton, "Delete" ElevatedButton (red/error color, initially disabled until input matches band name exactly)

**Leave Band:**
- Title: "Leave [band name]?"
- Body: "You will no longer be a member of this band."
- Actions: "Cancel" TextButton, "Leave" ElevatedButton (red/error color)

**Remove Member:**
- Title: "Remove [username] from [band name]?"
- Body: "[username] will no longer be a member of this band."
- Actions: "Cancel" TextButton, "Remove" ElevatedButton (red/error color)

## Interaction Patterns

### Navigation

- **Bands list → Band detail:** Tap band list item
- **Bands list → Create band screen:** Tap FAB, then "Create band" from menu (D-09)
- **Bands list → Join band dialog:** Tap FAB, then "Join with code" from menu (D-09)
- **Create/Join → Band detail:** After successful create/join, navigate to band detail screen (D-12, NOT back to list)
- **Band detail → Bands list:** After leaving or deleting band, pop back to list (D-15)
- **Band detail → Edit band:** Tap "Edit" action, open edit screen (edit is separate screen, mirrors create flow)

### Dialogs & Confirmations

- **Join code dialog (D-11):** Modal dialog, full keyboard, autofocus on text field
- **Delete band dialog (D-13):** Modal dialog, type-to-confirm pattern (delete button disabled until input matches exact band name)
- **Leave/Remove dialogs (D-14):** Standard material confirm dialogs (lighter than type-to-confirm)

### State Transitions

- **Optimistic updates:** After successful POST/PUT/DELETE, immediately update local cache before full refresh
- **Mutations:** All create/join/edit/leave/remove actions require network (no offline mutation queue per project constraints)
- **Snackbar/Toast notifications:** Brief confirmation ("Copied!", "Band created!", "Left band") after success — no toast errors (use inline error display instead)

## Accessibility & Platform Notes

### Flutter Specifics

- **Semantics:** All interactive elements (buttons, list items) have clear labels for screen readers
- **Touch targets:** Material minimum 48px height for tappable areas (ListTile default: 56px, buttons: 48px+)
- **Keyboard navigation:** Full keyboard support via Material widgets (tab through buttons, enter to confirm)
- **Dark mode:** Automatic via Material's `brightness` in ColorScheme (light/dark themes both defined in Phase 1)

### Platform Scope

- **Android:** Full support (native Android app)
- **iOS:** Full support (native iOS app)
- **Web:** Excluded this phase (web build not supported until later milestone)

## Design Decisions Pre-Populated From CONTEXT.md

Below summarizes locked decisions from `.planning/phases/02-bands/02-CONTEXT.md` that inform this contract:

| Decision | Implication for UI |
|----------|-------------------|
| D-01: Assume `Band.ownerId` and `UserProfile.id` are available from API | No fallback username-matching logic; owner-gating fully conditional on ID comparison |
| D-02: Owner-only actions (Delete, Remove member) hidden entirely for non-owners | Conditional widget visibility based on `Band.ownerId === profileProvider.id` |
| D-03: Owner cannot use "Leave band" — must delete instead | "Leave" button hidden when viewing own band as owner |
| D-04: Use existing `profileProvider` for current-user-id lookups | No new network call; reuse Phase 1's cache-first profile fetch |
| D-05: Band list shows name + avatar only (API schema is id+name) | No member count, genre, or other fields; avatar is separate BandAvatar widget |
| D-06: BandAvatar is reusable widget for future image swap | Initials rendered now; widget structure allows image URL drop-in later |
| D-07: Both list and per-band detail cached (one-box-per-endpoint pattern) | Requires `bandsBox` + per-band keyed cache in CacheService |
| D-08: Cache-first detail loading (show cached, refresh in background) | First-time load shows loading spinner; subsequent loads show cached detail immediately |
| D-09: Single FAB with action menu for Create/Join entry point | Bottom sheet or menu with two options, one FAB |
| D-10: Create band opens full screen (not dialog) | Consistent with other data-entry screens; allows form expansion later |
| D-11: Join band opens dialog (single field) | Modal dialog, lighter interaction than full-screen form |
| D-12: After successful create/join, navigate to band detail (not back to list) | Deep link into newly created/joined band's detail screen |
| D-13: Delete band uses type-to-confirm (user types band name to enable delete) | UI-only friction; locked behind exact text match; label "Delete" button while disabled |
| D-14: Leave/Remove use standard confirm dialog (interpolated copy, no typing) | Lighter confirmation than type-to-confirm; uses "Cancel" / "Leave"/"Remove" buttons |
| D-15: Deleting or leaving band returns user to Bands list | Pop navigation stack after destructive action completes |
