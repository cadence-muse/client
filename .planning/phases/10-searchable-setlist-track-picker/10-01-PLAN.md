<objective>
Add a search field to the existing setlist "add tracks" picker (`AddSetlistTracksDialog`) so a band member can quickly find the right track by title or artist even when the band has many tracks (ROADMAP Phase 10 goal; SETL-12).

Per D-01, this is additive to the existing `AlertDialog` shell — no full-screen picker, no change to the multi-select/add flow itself. Per D-03/D-04, the client documents and actually sends a `searchQuery` query parameter to `GET /api/band/{bandId}/track/list`, debounced 300ms, even though the backend currently ignores it (accepted forward-compatible wiring). Per D-05/D-06, this milestone's search only visibly filters **offline** (local substring match against the cached track list); **online**, the debounced request fires but the displayed list intentionally stays the full, unfiltered server response — a deliberate, accepted product tradeoff already flagged in STATE.md's Blockers/Concerns, not a bug.

Purpose: Let users find a track in a large band catalog fast, and lay the client-side wire contract now so the picker "just works" the moment backend filtering ships, with zero further client changes.
Output: Extended `lib/api/publicapi.yml`/`public_api.dart` (searchQuery spec + wire param), and a search-enabled `AddSetlistTracksDialog` with debounced online request + offline substring filtering, fully test-covered.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Search `TextField` (user-typed text) -> `ApiClient` query parameter | Untrusted user-typed text crosses into the HTTP request as a `searchQuery` query-string parameter on an already-authenticated, already-band-scoped request. |
| Cached track list (local storage) -> offline substring filter | Purely client-side: the offline filter reads only data the user already fetched and is authorized to see (their own band's cached track list) — no new data surface is read or displayed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-01 | Tampering (Injection) | `public_api.dart` `listBandTracks()` -> `ApiClient.send(queryParameters:)` | medium | mitigate | The search string is passed through `Uri(...).replace(queryParameters: {...})`, which percent-encodes the value — never string-interpolated directly into the URL path or a raw query string. No client-side SQL/shell execution occurs. Full backend-side query-injection hardening is out of this phase's scope (backend currently ignores the field entirely); canon OWASP-injection concern breadcrumbed to `/gsd-secure-phase` + backend milestone rather than minted as a bespoke prohibition here. |
| T-10-02 | Elevation of Privilege (Access Control) | `listBandTracks(bandId, searchQuery)` request scope | low | accept | The `bandId` path parameter (not user-controlled free text) already scopes the request server-side to a single band; `searchQuery` only narrows within that pre-authorized scope and cannot expand it to another band's tracks — same authorization boundary as the pre-existing endpoint, unchanged by this phase. Canon OWASP-broken-access-control concern breadcrumbed to `/gsd-secure-phase`; no new boundary is introduced here. |
| T-10-03 | Information Disclosure | Offline local substring filter reading `trackListDataProvider`'s cache | low | accept | Filtering operates purely on data the user has already fetched and is authorized to see; no new data surface is read, cached, or displayed. |
| T-10-04 | Denial of Service (client-side request spam) | Debounced `listBandTracks` call armed per keystroke pause | low | mitigate | 300ms debounce `Timer` (D-04) coalesces keystrokes into at most one request per pause; the timer is canceled in `dispose()` and never re-armed while offline (Task 2), so no wasted/duplicate requests accumulate. |
| T-10-05 | Repudiation / Spoofing | N/A — no new identity or audit surface | low | accept | Existing `sessionAuth` (Authorization header) is unchanged; this phase introduces no new authentication or logging surface. |
