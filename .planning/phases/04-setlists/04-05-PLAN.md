<objective>
Add the global, cross-band Setlists tab (SETL-10): a new bottom-nav tab showing a flat list of every setlist across every band the user belongs to, with a band-name badge per row and a filter dropdown to narrow to one band — mirroring Phase 3's `TracksScreen`/`UserTracksListData`/`SelectedBandIdFilter` shape exactly. This plan also carries out D-21's bottom-nav reorder (Home/Bands/Tracks/Setlists/Profile), a deliberate change beyond just appending the new tab.

**Architecture note (singular -> plural transition, mirrors Phase 3 03-03's identical note):** this plan introduces Phase 4's only per-entity -> cross-entity transition — a single band's setlist list (Plan 01/02/03/04, keyed by `bandId`) versus a view spanning *all* of a user's bands. Decision: **add-alongside**, not promote. The primary identity/key model for a setlist stays per-band-scoped (`(bandId, setlistId)`, matching every mutation endpoint — create/update/delete/track-add/track-remove/reorder all live under `/api/band/{bandId}/setlist/...`). The global view is an additive, read-only aggregate sourced from a separate endpoint (`GET /api/setlist/list`, `UserSetlistListItem` — a distinct, wider shape carrying `bandId`/`bandName`) and a separate provider (`UserSetlistsListData`), not a promotion of the per-band model to "primary". Rationale: every write operation is still band-scoped by the API contract; promoting the global view to primary would require inventing a cross-band identity the backend doesn't expose.

**Naming deviation — `SelectedSetlistBandIdFilter`, not `SelectedBandIdFilter`:** `lib/providers/tracks_provider.dart` already defines a plain provider named `SelectedBandIdFilter` (generated as `selectedBandIdFilterProvider`) for the Tracks tab's own band filter. `lib/features/setlists/add_setlist_tracks_dialog.dart` (Plan 03) imports both `tracks_provider.dart` (for `trackListDataProvider`) and `setlists_provider.dart` (for `setlistDetailDataProvider`) in the same file — if `setlists_provider.dart` also defined a top-level `SelectedBandIdFilter`/`selectedBandIdFilterProvider`, any file importing both provider files would hit a Dart "ambiguous import" compile error on that identifier. This plan therefore names the setlist-scoped filter provider `SelectedSetlistBandIdFilter` (generated `selectedSetlistBandIdFilterProvider`) — functionally identical to Track's filter, distinctly named to avoid the collision. Do not "fix" this to match Track's name; the distinct name is required, not a stylistic slip.

Purpose: close the last Phase 4 requirement (SETL-10) so the full setlist feature set (SETL-01 through SETL-10) is complete.
Output: `SetlistsScreen` (new bottom-nav tab), the `listUserSetlists` API method, and the `UserSetlistsListData`/`SelectedSetlistBandIdFilter` providers, plus `root_scaffold.dart`'s reordered navigation.
</objective>
