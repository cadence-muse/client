<objective>
Stand up the per-band setlist view + create path end-to-end: a band member can view a band's setlists, create a new one (with an optional inline multi-select of the band's existing tracks), and open a setlist's detail page showing its ordered tracks and server-computed running duration. This is the tracer slice for Phase 4 — it wires every layer (API contract calls, Hive cache, Riverpod family providers, three new screens, and the Band Detail navigation entry point) for SETL-01/02/03/09 in one production-quality path, mirroring Phase 3's `TrackListData`/`TrackDetailData`/`TrackListScreen`/`CreateTrackScreen`/`TrackDetailScreen` shape exactly rather than inventing a new one.

Track add/remove, drag-and-drop reorder, edit/delete setlist info, and the global cross-band Setlists tab (SETL-04 through SETL-08, SETL-10) build on top of this plan's artifacts in Plans 02 through 05.

**Note on duration/date formatting:** this phase introduces a distinct duration format from Phase 3 — `'42m 35s'` (words, per D-05/UI-SPEC Copywriting Contract), not Track's `'3:45'` (colon mm:ss). A new `asMinutesAndSeconds` getter is added to `setlist_formatting.dart` rather than reusing `track_formatting.dart`'s `asMinutesSeconds` — the two features intentionally use different duration presentations per their respective UI-SPECs.

**Note on error copy:** this phase's list/detail load-failure copy is `'Failed to load setlists. Tap to try again.'` (single line, per 04-UI-SPEC.md's Copywriting Contract "Error & Status Messages" table), not Phase 3 Tracks' two-line `"Couldn't load tracks"` + `'Please check your connection and try again.'` block. Keep the existing heading+body+Retry-button *structure* (proven, accessible, matches every other screen in the app) but substitute the Setlist-specific single-line copy as the body text with no separate heading line.

Purpose: prove the Riverpod + Hive cache-store pattern generalizes to a fourth per-band-keyed entity (after bands, tracks, and — within this feature — a track-array-bearing detail shape) without architectural surprises, before expanding into track add/remove/reorder/edit/delete/global-view.
Output: `SetlistListScreen`, `CreateSetlistScreen`, `SetlistDetailScreen` (read-only in this plan — no edit/delete/track-mutation UI yet, those land in Plans 02-04), the `SetlistListData`/`SetlistDetailData` providers, and their `CacheService`/`PublicApi` backing methods — all reachable from `BandDetailScreen`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client -> Cadence backend API | `PublicApi.listBandSetlists`/`getSetlist`/`createSetlist` cross the network; responses are untrusted until parsed by the client |
| User input -> CreateSetlistScreen form | Name/location/date/selected-track-ids are untrusted free text/selections entered on-device before being sent to the server |
| App -> device-local Hive setlistsBox | Cached setlist lists/details (incl. event location/date and track arrays) persist in the app's private sandboxed storage |
