Users enter track duration as mm:ss on the create and edit track forms. Typing digits auto-formats them into mm:ss shape as the user types (no manual colon entry), backspace deletes the last shifted digit and reformats, the field caps at 99:59, and an invalid value (seconds >= 60, malformed/incomplete text) is rejected with inline error text on submit — matching the existing WR-02 validation-timing pattern. A blank field stays optional and submits `durationSeconds: null`, unchanged from today. The API contract itself does not change; conversion happens only at the input/display boundary.

Purpose: DUR-01, DUR-02, and DUR-04 require the create/edit track forms to accept and validate mm:ss input instead of raw seconds, per the user's locked D-02/D-03/D-04/D-05/D-06 decisions in `11-CONTEXT.md`.

Output: `DurationTextInputFormatter` + `parseDurationSeconds()` in `track_formatting.dart`, wired end-to-end into both `create_track_screen.dart` and `edit_track_screen.dart`, with unit tests for the formatter/parser and updated/new widget tests proving the full type -> format -> validate -> submit path.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| User keystroke/paste -> DurationTextInputFormatter | Untrusted raw text input crosses into the formatter/validator/parser chain before becoming the `durationSeconds` value sent to the API |
| Form submit -> PublicApi.createBandTrack/updateBandTrack | Validated `durationSeconds` int crosses into the existing, unchanged wire boundary (`publicapi.yml`) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-01 | Tampering | `_durationValidator`/`parseDurationSeconds()` in create/edit track screens | medium | mitigate | Both functions independently re-check `seconds > 59` and `minutes/seconds < 0` at submit time, not trusting `DurationTextInputFormatter`'s shape-only output — catches a validation bypass via paste or programmatic `controller.text` assignment |
| T-11-02 | Tampering | `DurationTextInputFormatter.formatEditUpdate` | low | mitigate | 4-digit cap (not 5, per the digit-cap correction in `<context>`) bounds minutes to 2 digits, enforcing D-03's literal "99:59 maximum" at the formatter layer; combined with T-11-01's submit-time seconds check, no oversized or malformed value reaches `durationSeconds` |
| T-11-03 | Denial of Service | `DurationTextInputFormatter` (keystroke-rejection path) | low | accept | Rejected keystrokes (>4 digits) simply revert to `oldValue` — no unbounded loop or allocation; this is a single client-side text field, not a shared resource |
| T-11-04 | Injection | `parseDurationSeconds()` -> `durationSeconds: int` on the wire | low | accept | `durationSeconds` is a plain integer in the API contract; no string concatenation into a query/command, so no injection vector exists via this field |
</threat_model>
