## Design Decisions (Locked from Phase 5 Context)

| Decision | Value | Rationale |
|----------|-------|-----------|
| **D-01: Connectivity Detection** | `connectivity_plus` package; device radio/interface state, not reachability ping | Chosen over active ping; accepts known gap (captive portal false-positive) as reasonable v1 tradeoff |
| **D-02: Connectivity State** | Single global `StreamProvider<ConnectivityStatus>` in Riverpod, watched by banner + mutation entry points + Save buttons | One source of truth, consistent with Riverpod-everywhere pattern (Phases 1-4) |
| **D-03: Connectivity Debounce** | No debounce on sub-second blips (e.g., switching wifi APs) | Instant state flip accepted for v1 scope |
| **D-04: Timestamp Storage** | Every cache write wraps as `{data: {...}, syncedAt: isoString}` instead of raw JSON | Chosen over parallel timestamp store to avoid two-stores-can-drift risk |
| **D-05: Timestamp Granularity** | Per cache key (not per screen) — every keyed entry gets independent `syncedAt` | Matches existing one-entry-per-key cache shape (bands list, `band_<id>` detail, tracks list, etc.) |
| **D-06: Silent Refresh Failure** | On background-refresh failure, `syncedAt` NOT updated; stays at last successful write | Keeps staleness indicator honest (correctly escalates to warning when refreshes fail) |
| **D-07: Indicator Placement** | Below AppBar, above screen content (shared widget position on all cached screens) | Consistent placement convention across list and detail screens |
| **D-08: Warning Escalation** | Color + icon change only (neutral grey → warning amber/orange), no copy/layout shift | Minimal visual disruption; escalation is recognizable but not jarring |
| **D-09: Indicator Visibility** | Hidden <10m old, counts up from 10m, escalates to warning color at 30m | Hides noise (fresh data doesn't need indicator); threshold independent from warning threshold |
| **D-10: Banner Placement** | Wraps `RootScaffold.body` above `IndexedStack` and above `NavigationBar` | Single implementation point; shows/hides on every tab |
| **D-11: Mutation Disabling** | FABs, Save buttons, destructive actions disabled + visually grayed out while offline | "Visibly disabled" per OFFL-03; not hidden, not silently tap-blocked |
| **D-12: Mutation Blocking** | Blocked at source (FAB/button disabled); user never reaches a form they can't submit | No drafting-while-offline flow; consistent with read-only-cache scope (no offline mutation queue) |
| **D-13: Disabled Feedback** | Tooltip "Requires connection" on tap/long-press of disabled control | Communicates why control is inactive without silent inertness |
| **D-14: Live Form Reaction** | If form open while online, then connectivity drops, Save button disables immediately | Watches same D-02 connectivity provider; reacts live to state changes |

## Interaction Model: Offline State Transitions

### Scenario 1: User Opens App, Loads Data, Then Goes Offline

1. Screen loads data from API, writes to cache with `syncedAt = now`
2. Staleness indicator hidden (<10m old)
3. Offline banner hidden (device online)
4. All mutation FABs/buttons enabled
5. User turns off wifi/enters airplane mode
6. Offline banner appears instantly: "You're offline — showing cached data"
7. All mutation FABs/buttons disable with opacity reduced to ~38%
8. Tap any disabled button → tooltip "Requires connection" appears
9. Data stays visible (cache-first already provided this)
10. Screen still shows staleness indicator if now >10m old
11. User reconnects
12. Offline banner disappears instantly
13. Mutation FABs/buttons enable instantly
14. Background refresh may occur (if triggered), updating `syncedAt` on success

### Scenario 2: User Tries to Mutate While Offline

1. User taps Create Band FAB (intended action)
2. FAB is already disabled (grayed, ~38% opacity), does not open form
3. Tap registers; tooltip "Requires connection" appears
4. User cannot proceed without reconnecting
5. If already on an open form (Edit Band), Save button is already disabled
6. Same tooltip appears on Save button
7. No data loss; form state preserved until reconnect

### Scenario 3: Staleness Escalation

1. Data cached at 10:00 AM, `syncedAt = "2026-08-17T10:00:00Z"`
2. At 10:09 AM: indicator hidden (9m old)
3. At 10:10 AM: indicator appears "Synced 10m ago" in onSurfaceVariant grey
4. At 10:39 AM: indicator still "Synced 39m ago" in same grey color
5. At 10:30 AM: icon + text color changes to warning amber/orange (but text still reads "Synced 30m ago")
6. User refreshes; new data cached at 10:30 AM, `syncedAt` updates to now
7. Indicator resets to "Synced 0m ago" (or hidden if 0-1m), grey color
