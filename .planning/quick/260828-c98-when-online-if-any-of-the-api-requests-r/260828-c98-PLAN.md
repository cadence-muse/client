<objective>
When the app is online and any authenticated API request comes back with a 401, treat it exactly
like the existing 403 auto-logout: clear the locally stored session token, fall back to the login
screen, and additionally show a one-time "Session expired" SnackBar on that login screen so the
user understands why they were kicked out. A manual "Log out" from the Profile screen must
continue to be silent (no toast).

Today `ApiClient.send()` (`lib/api/api_client.dart`) only special-cases `403` -- calling
`onUnauthorized()` (wired to `AuthSession.signOut()`) and throwing. A `401` currently falls through
to the generic `>= 400` branch: it throws an `ApiException` but never clears the session or
navigates anywhere. There is also no "why was I logged out" signal anywhere today, so
`LoginScreen` (`lib/features/auth/login_screen.dart`) cannot distinguish a forced session-expiry
sign-out from a manual one or a cold start.

Purpose: Prevent the app from silently sitting on a dead/expired session and confusingly failing
every subsequent request with an unhandled 401 error; give the user a clear, one-time explanation
when that happens.
Output: `ApiClient` triggers the existing auto-logout path for 401 as well as 403;
`AuthSession.signOut()` gains an optional `sessionExpired` flag consumed exactly once by
`LoginScreen` to show a new `loginSessionExpiredSnackbar` ("Session expired") message.
</objective>

Key facts gathered from reading the above:

- `ApiClient.send()` currently does `if (response.statusCode == 403) { await onUnauthorized();
  throw ApiException.fromResponse(response); }` then a separate `if (response.statusCode >= 400)
  { throw ApiException.fromResponse(response); }`. `401` is not defined anywhere in
  `lib/api/publicapi.yml` per-endpoint responses (only `400` is documented there), same as `403`
  -- both are middleware-level auth failures outside the per-operation OpenAPI contract, so
  extending the same special-case to `401` does not conflict with the spec.
- `onUnauthorized` is wired in `lib/providers/auth_provider.dart`'s `apiClientProvider` to
  `() => ref.read(authSessionProvider.notifier).signOut()`.
- `AuthSession` (same file, `@riverpod class AuthSession extends _$AuthSession`) already has a
  `_loggingOut` reentrancy guard on `signOut()` (a 403/401 on the best-effort `logout()` network
  call inside `signOut()` itself must not recurse unboundedly).
- `signOut()` is also called directly, with no arguments, from
  `lib/features/profile/profile_screen.dart`'s "Log out" `ListTile.onTap` -- this manual path must
  keep behaving identically (no toast).
- `LoginScreen` is a `ConsumerStatefulWidget`/`ConsumerState` (has `ref` available in lifecycle
  methods) that currently only overrides `dispose()`, not `initState()`.
- `AuthGate` shows `const LoginScreen()` whenever `authSessionProvider` resolves to a null token --
  this covers cold start (never signed in), manual sign-out, and forced sign-out identically, so
  `LoginScreen` itself must be the one to decide whether to show the toast (via a flag it reads
  off `AuthSession`), not `AuthGate`.
- ARB files (`lib/l10n/app_en.arb` / `app_ru.arb`) are flat key-value, no `@key` metadata blocks
  used anywhere in the `login*` section; generated Dart output under `lib/generated/` is committed
  to git and regenerated via `flutter gen-l10n` (`generate: true` in `pubspec.yaml`,
  `output-dir: lib/generated` in `l10n.yaml`) -- **not** via `build_runner`, which is a documented
  no-op for this project's l10n pipeline (see `.planning/milestones/v1.2-phases/13-*` SUMMARY).
  `flutter` is at `/home/bulat.khafizov/software/flutter/bin/flutter` in this environment.
- `test/test_strings.dart`'s `tester.strings.someKey` reads the live `AppLocalizations` instance
  off the pumped widget tree, so a new ARB key is usable in tests immediately after
  regeneration -- no separate test-string registration needed.
- `test/providers/auth_provider_test.dart`'s `buildContainer()` helper does **not** use the real
  `apiClientProvider` from production code -- it overrides it with its own inline `ApiClient(...)`
  construction that intentionally mirrors the production wiring (see that file's doc comment:
  "mirroring the real apiClientProvider ... so tests can exercise the logout call's ... path").
  Any change to production's `onUnauthorized` wiring must be mirrored in that test helper too, or
  the test suite silently stops reflecting production behavior.
- No existing test anywhere in `test/` mocks a `401` response today -- there is no regression risk
  from a pre-existing test relying on `401` *not* triggering auto-logout.
