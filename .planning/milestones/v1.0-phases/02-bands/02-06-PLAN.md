<objective>
Close the 4 verification gaps from `02-VERIFICATION.md` that keep Phase 2 from actually delivering "the Riverpod + cache-store pattern from Phase 1" and production-safe mutations:

1. **CR-01 (blocker):** `_HiveStore.get()` only shallow-converts the top-level map read from Hive; nested Map/List values (e.g. a band's `members` list) come back as Hive's untyped `Map<dynamic, dynamic>`/`List<dynamic>` and throw `TypeError` on first access — but every existing test used `CacheService.inMemory()`, which never round-trips through Hive's binary format, so this went undetected through 5 completed plans and 53 passing tests.
2. **WR-02 (race):** `BandsListData`/`BandDetailData`'s unawaited background `_refresh()` unconditionally overwrites state with fetched data, with no guard against a local mutation (`setBands`/`updateName`) having landed after the refresh started — so a slow background refresh can silently revert a just-applied edit.
3. **WR-01 (stale list):** `EditBandScreen` never touches `bandsListDataProvider` after a successful rename, so `BandsScreen` (kept alive in `RootScaffold`'s `IndexedStack`) shows the old name until an unrelated manual refresh.
4. **WR-03 (silent failures):** all 6 mutation call sites only catch `ApiException`, so offline/parse/cache failures re-enable the submit button with zero user feedback.

This is gap-closure only — the 9 band-management features shipped in 02-01 through 02-05 are not re-planned or re-touched beyond what these 4 fixes require.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Hive on-disk cache <-> in-app Dart types | `_HiveStore.get()`'s deserialization path is the boundary between whatever bytes exist on disk (written by this app's own prior sessions — not directly attacker-controlled, but a boundary nonetheless: corrupted/partial writes, cross-version schema drift, or a compromised device's tampered Hive file all produce "malformed" shapes at this boundary) and the typed `Map<String, dynamic>` the rest of the app trusts |
| Flutter app <-> API server | Unchanged by this plan — all 6 mutation catch-blocks still only ever see exceptions already flowing through the existing `ApiClient`/`ApiException` boundary or local runtime errors; no new network surface is introduced |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Tampering / Denial of Service (malformed local cache data) | `lib/cache/cache_service.dart` (`_HiveStore._deepConvert`) | medium | mitigate | `_deepConvert` recurses only over the actual shape written by this app's own `writeBands`/`writeBandDetail` calls (bounded depth — Band/BandMember's schema is shallow, no cycles possible since JSON has none); if a corrupted/foreign Hive file produces a `key` that isn't a `String` (Hive's `readKey()` only ever writes `uintT`/`utf8StringT` for this app's Map<String,dynamic> keys, so this shouldn't occur in practice), the `key as String` cast throws, which is caught by the existing outer `try {...} catch (_) { return null; }` in `readBands()`/`readBandDetail()` — the app fails open to a cache miss (triggers a fresh network fetch) rather than crashing, so a malformed cache entry degrades gracefully instead of taking down the screen |
