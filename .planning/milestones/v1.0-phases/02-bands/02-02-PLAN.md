<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flutter app <-> API server | `GET /api/band/{bandId}` crosses the network trust boundary; response (including `ownerId`, `inviteCode`) is untrusted input decoded and cached client-side |
| App <-> Clipboard | `Clipboard.setData` writes the invite code to the OS-shared clipboard, which other apps on the device can read |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05 | Information Disclosure | `lib/features/bands/band_detail_screen.dart` (invite code display/copy) | medium | accept | Invite codes are server-generated and server-validated; the client has no code-generation/prediction logic and does not log the code; brute-force/rate-limiting protection is a server-side concern outside this phase's control. Clipboard exposure to other apps is an accepted platform-level tradeoff of the copy-to-share UX this feature explicitly requires (BAND-07) |
| T-02-01 | Tampering / Elevation of Privilege | `lib/providers/bands_provider.dart` (`BandDetailData` — first place `Band.ownerId` enters the app) | high | mitigate | `ownerId` is read verbatim from the server response and never derived from client input; no owner-gated UI decision is made in THIS plan (detail is read-only here) — the actual gating comparison lands in 02-05, where this threat is re-confirmed against the concrete mitigation (D-01/D-02: compare server-returned `ownerId` to server-returned `UserProfile.id`, never a client-supplied id) |
</threat_model>
