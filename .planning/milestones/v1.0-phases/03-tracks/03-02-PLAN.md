## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client -> Cadence backend API | `updateBandTrack`/`deleteBandTrack` cross the network; the server is the sole authority on whether a given user may mutate a given track |
| User input -> EditTrackScreen form | Edited title/artist/duration/tempo/key/notes are untrusted free text re-submitted to the server |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-06 | Tampering | PUT /api/band/{bandId}/track/{trackId} (updateBandTrack) | low | accept | Server validates and is authoritative; client merges its own submitted values into cache rather than trusting a response body (there isn't one), so a manipulated client-side merge can at most display stale local UI, never persist server-side beyond what the server itself accepted. |
| T-03-07 | Repudiation | DELETE /api/band/{bandId}/track/{trackId} (deleteBandTrack) | low | accept | Deletion is immediate and irreversible per D-11 (lightweight confirm, no undo); this matches the accepted-risk pattern already used for Leave Band / Remove Member in Phase 2 — no audit trail requirement in scope for v1. |
| T-03-08 | Elevation of Privilege | Edit/Delete track access (any band member, no owner-only path) | low | accept | TRACK-04/TRACK-05 carry no owner qualifier; RESEARCH.md V4 Access Control confirms server-side enforcement is band-membership-scoped only; client intentionally adds no ownership gate (see this plan's objective note resolving the UI-SPEC discrepancy). |
</threat_model>
