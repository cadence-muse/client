## Phase Goal

**As a** band member, **I want to** view my profile and homepage summary in an app now running on Riverpod state management with a working local cache layer, **so that** every later phase (bands, tracks, setlists) can build directly on proven state-management and offline-caching patterns instead of retrofitting them.

*(User story reformatted from ROADMAP.md Phase 1 `**Goal:**` line; this plan proves the story's Profile half end-to-end. 01-03-PLAN.md proves the Homepage half.)*

- [ ] No `ChangeNotifier`/`ValueNotifier` remains reachable from the app shell — auth and theme are Riverpod-native
- [ ] `ApiClient`/`PublicApi`/`TokenStorage` construction lives inside `ProviderScope`, not `main()`

Context-budget.md's "Heavy (migrations, multi-subsystem)" category explicitly allows a single ~30-40% task for exactly this shape of work.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> API (`GET /api/me`) | Session cookie sent to `AppConfig.apiBaseUrl`; untrusted JSON response parsed and rendered |
| Client -> Hive local storage | App writes/reads locally-persisted, unencrypted JSON blobs (profile data only) |
| Client -> flutter_secure_storage | Auth token persisted via platform Keychain/Keystore, unchanged this phase |
| Device (multi-user) -> cached UI | Cached data is visible to whoever currently controls the device/app session |
