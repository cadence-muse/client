## Interaction & State Handling

### Search Behavior (D-02 to D-06)

1. **User types in search field:**
   - Each keystroke triggers the debounce timer (300ms, D-04)
   - Text is captured and stored in local state (`_searchQuery`)
   - Timer resets on each new keystroke

2. **After 300ms debounce expires:**
   - **Online mode (D-05 + isOnlineProvider):**
     - Append `?searchQuery={_searchQuery}` to GET `/api/band/{bandId}/track/list` request
     - Send debounced network request (currently ignored by backend; full list returned)
     - UI displays server response as-is (no client-side filtering)
     - User sees unfiltered list (accepted tradeoff per D-06, flagged in STATE.md)
   - **Offline mode (D-05):**
     - Do NOT attempt network request (isOnlineProvider false)
     - Filter cached `trackListDataProvider` results locally using substring match on title + artist (case-insensitive, D-02)
     - Display filtered results or "No tracks match your search" if zero matches (D-07)

3. **User clears search field:**
   - Debounce timer expires with empty `_searchQuery`
   - Network request may still fire (empty query param), or no-op based on implementation choice (Claude's Discretion)
   - Cached list returns to full display (offline) or server's full list (online)

4. **User navigates away:**
   - Dialog closes; search state is discarded (no persistence across dialog reopen)

### Loading & Error States (unchanged from existing dialog)

- **Initial load:** `CircularProgressIndicator` centered in dialog
- **Load failure:** "Couldn't load tracks" text + "Retry" button
- **Submit error:** `_errorMessage` displayed in red at bottom of dialog
- **Submit in flight:** "Add" button shows spinner, disabled

### Selection & Submission (unchanged)

- Max 100 tracks per setlist; remaining slots calculated after search filter
- User selects/deselects via checkbox taps
- "Add" button disabled if:
  - No tracks selected, OR
  - Offline (`!isOnline`), OR
  - Submit in flight (`_isSubmitting`), OR
  - All remaining slots filled (cap reached)
- Success: Dialog closes, SnackBar "Tracks added!" shown, providers refreshed (setlist detail, setlist list, user setlists)

## Provider & Data Flow

### Search Query State

Search input text stored in `_searchQuery` (local StatefulWidget state, not Riverpod — no persistence needed).

### Track List Provider: Unchanged Signature (Claude's Discretion)

`trackListDataProvider(bandId)` remains keyed by `bandId` only, unchanged from existing usage across 6+ call sites. Rationale:
- Avoids polluting the shared cache with search-variant keys
- Search request sent to wire (`/api/band/{bandId}/track/list?searchQuery=...`) but client-side result keying stays stable
- Offline filtering applied to the cached result in-widget, not at provider level
- Future backend support for `searchQuery` can reuse the same provider without cache collision

### Public API Method

`public_api.dart:listBandTracks(String bandId)` method signature extended with optional parameter:

```dart
Future<List<Map<String, dynamic>>> listBandTracks(
  String bandId, {
  String? searchQuery,
}
)
```

GET request URL: `/api/band/{bandId}/track/list?searchQuery={searchQuery}` (only appended if `searchQuery` is non-empty per D-03)

### Spec Extension

`lib/api/publicapi.yml` `ListBandTracks` operation gains `searchQuery` query parameter (D-03):

```yaml
parameters:
  - name: searchQuery
    in: query
    required: false
    schema:
      type: string
    description: "Search by artist or title match (substring, case-insensitive). Server currently ignores this field; client-side filtering applies offline only."
```
