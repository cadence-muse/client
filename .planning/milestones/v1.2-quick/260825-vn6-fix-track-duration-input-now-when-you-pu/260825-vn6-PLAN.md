<objective>
Fix `DurationTextInputFormatter.formatEditUpdate` in `lib/features/tracks/track_formatting.dart` (shipped in Phase 11, `11-01-PLAN.md`): typing a digit into the Duration field on the create/edit track forms blocks further input almost immediately, only unblocking when the user manually deletes one of the leading zeros the formatter itself inserted.

Root cause: on every keystroke the formatter re-derives the "raw digits typed so far" by stripping non-digit characters from the field's *currently displayed* text. In real usage that displayed text is whatever the formatter itself last rendered — e.g. after typing a single "2" the field shows "0:02". That "0:02" already contains 3 digit characters (two of them synthetic zero-padding this formatter injected, not something the user typed). The next keystroke re-counts all of those as if the user had typed them, so the digit count balloons past the 4-digit safety cap after just 2-3 real keystrokes and the field appears to lock up — exactly what the user reported. The formatter's own existing unit tests never caught this because each test case calls `formatEditUpdate` in isolation with a hand-built raw-digit `oldValue` (e.g. `value('23')`), not the actual formatted output ("0:23") a real chained keystroke sequence would produce — so they don't exercise the failure at all.

Purpose: Restore usable Duration input on the create/edit track forms (Phase 11, DUR-04) without touching the submit-time validation chain (`_durationValidator`/`parseDurationSeconds`), which is independently correct and untouched by this bug.

Output: A corrected `DurationTextInputFormatter.formatEditUpdate` that tracks the truly-typed raw digit count via a diff against the previous state instead of re-parsing the full displayed (already-formatted) text, plus regression tests that simulate real chained keystrokes (each call's `oldValue` is the literal output of the previous call) — the only way to reproduce and prove the fix for this bug.
</objective>

    In `lib/features/tracks/track_formatting.dart`, replace the body of `DurationTextInputFormatter.formatEditUpdate`. Keep the class's existing empty-input early return unchanged (when digits stripped from `newValue.text` are empty, return `newValue.copyWith(text: '', selection: collapsed(0))`). Keep the existing 4-digit cap check unchanged (`return oldValue` when the computed raw digit buffer exceeds 4 characters) and the existing formatting branch unchanged (`<=2` digits pads to `'0:' + digits.padLeft(2, '0')`; `>2` digits splits into a minutes substring and a 2-character seconds substring). Keep the existing final return unchanged (`newValue.copyWith(text: formatted, selection: TextSelection.collapsed(offset: formatted.length))`).

    The only change is how the raw digit buffer is computed. Add a new private top-level function `_rawTypedDigits(String formatted)` that recovers the count of digits the user actually typed from a previously-rendered `mm:ss` string, undoing this formatter's own synthetic zero-padding (the leading `'0:'` minutes placeholder and the seconds `padLeft(2, '0')`) — this is what the current buggy implementation fails to do, since it re-parses the full *displayed* text as if every character were user-typed. Implement it: if the input is empty, return `''`. Split on `':'`; if the split does not produce exactly 2 parts, return the input with all non-digit characters stripped (defensive fallback covering the pre-existing isolated unit tests, which pass raw digit strings like `'23'` as `oldValue.text` rather than formatted `mm:ss` text). Otherwise, with `minutes` and `seconds` as the two parts: if `minutes != '0'`, return `minutes + seconds` (exact — the 3-4 digit formatting branch never pads, so concatenation recovers the original digit sequence with no ambiguity). If `minutes == '0'`: when `seconds == '00'`, return `'0'`; when `seconds` is exactly 2 characters, starts with `'0'`, and is not `'00'`, return `seconds` with that one leading zero stripped (undoes the single-digit `padLeft`); otherwise return `seconds` unchanged. Add a doc comment on `_rawTypedDigits` noting this is a best-effort inverse — for a `minutes == '0'` display the true prior digit count is inherently ambiguous between 1 and 2 typed digits (both pad identically), but both interpretations format identically and parse to the same duration, so the ambiguity is harmless; there is no ambiguity when `minutes != '0'`.

    In `formatEditUpdate`, compute `digitsNew` (digits stripped from `newValue.text`, as today) and `digitsOld` (digits stripped from `oldValue.text`). Compute `oldRaw = _rawTypedDigits(oldValue.text)`. Determine the raw digit buffer: if `digitsNew.length >= digitsOld.length` and `digitsNew` starts with `digitsOld`, this is an append at the end (the common typing/paste-at-end case, since the cursor is always collapsed to the end by this formatter's own prior return) — set the raw digit buffer to `oldRaw + digitsNew.substring(digitsOld.length)` (only the newly-added suffix is appended to the previously-typed digits; `digitsOld`/`digitsNew` are used solely to locate which characters are new, never trusted as the raw digit count itself — that distinction is the actual fix). Else if `digitsNew.length < digitsOld.length` and `digitsOld` starts with `digitsNew`, this is a removal from the end (ordinary backspace) — let `removed = digitsOld.length - digitsNew.length` and set the raw digit buffer to `oldRaw.substring(0, oldRaw.length - removed)` when `oldRaw.length > removed`, else `''`. Otherwise (full replace/paste over a selection, or a mid-string edit) set the raw digit buffer to `digitsNew` directly, trusting the new text's digits as the raw source. Feed this raw digit buffer into the unchanged cap-check/formatting/return logic described above.
